05 智能体工具集成 · 串联关系

数据库只保存“叫什么”，进程注册表才保存“怎么执行”。两边用同一个工具名接上，会话时再把数据库记录还原成可调用对象。

Registry["get_weather"]=tools.name=ToolCall.function.name

主链：上一步的产出就是下一步的输入

1

启动时，函数进入内存

inits.Init 调用 tools.RegisterBuiltins，读取 weather.apiKey，构造 WeatherTool 并放进进程内 Registry。

输入配置中的高德 Key
→
输出可通过 get_weather 找到的 InvokeParamTool
Key 只存在这个内存对象里。数据库和接口响应都不会保存它。
2

登记时，用名字从内存取契约，再写入数据库

POST /api/v1/tools 收到 name=get_weather 后调用 FindTool。找不到就返回 3003，不会凭请求正文造一个工具。

从注册表取Info.Name、Info.Desc、Params()
→
写入 toolsname、description、parameters_schema、creator_id

因此系统工具的中文展示名不能作为查找键，注册名必须和代码一致。

3

绑定时，只保存关系，不复制函数

POST /api/v1/agents/{id}/tools/batch 先确认智能体属于当前用户，再通过 getToolsInIds 事件取出工具并核对创建者。

输入工具 UUID 列表
→
输出清空该智能体旧关联后，重建 agent_tools

关联记录只有 agent_id、tool_id、status=enabled。工具定义仍留在 tools。

4

会话加载时，关系被还原成注册表对象

GetAgentWithTools 预加载关联工具。对每条启用的 system 记录，用它的 name 回到第 1 步的 Registry。

数据库给出tools.name = get_weather
→
注册表交回同一个可执行的 WeatherTool
名称对不上时不会报错中断对话，只记录警告并跳过该工具。所以第 2 步必须保存注册名。
5

模型同时拿到两份描述，但只有一份能真正发调用

协议绑定chatModel.WithTools(ToolInfo)，模型据此生成结构化 ToolCall
+
文字提示BaseSystemPrompt 的 {toolsInfo}，说明何时使用

三家厂商适配器都返回 ToolCallingChatModel，所以绑定发生在同一次对话模型上。没有关联工具时，这一步退回原来的直接流式回答。

6

调用闭环：模型给出参数，工具返回文本，模型继续回答

Stream 得到完整消息；若有 ToolCall，就按 function.name 找到第 4 步还原的对象，执行 InvokableRun(arguments)。高德返回的 JSON 字符串被放进 ToolMessage(content, call.ID)，追加到消息后再次请求模型。没有 ToolCall 或达到 4 轮时停止。
模型 → 工具{"city":"北京","extensions":"base"}
→
工具 → 模型高德响应原文；失败时是错误文本，不是抛出给前端中断

测试是主链的短路

POST /api/v1/tools/{id}/test 不经过智能体和模型：当前用户的 tools 记录 → 检查启用 → FindTool(name) → 同一个 InvokableRun。它验证的是第 1 步和第 2 步已经接上，不验证第 3 步的智能体关联。

每一跳保存什么

位置保存不保存
Registry函数、参数定义、高德 Key用户、智能体关系
tools注册名、描述、参数 schema、所有者函数和 Key
agent_toolsagent 与 tool 的 ID 关系工具定义副本
本次请求消息ToolCall 与 ToolMessage下次请求看不到本次结果

断点

  1. Key 为空：链路可登记，但第 6 步调用失败。
  2. MCP 只有配置入库，buildTools 会跳过，测试也不会发起请求。
  3. 关联替换先删后插，两次写库没有事务。
  4. 对话没有会话存储，工具结果不跨 HTTP 请求保留。
